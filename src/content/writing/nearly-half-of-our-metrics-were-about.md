<p>For most of this year we were paying to store a family of metrics that nobody had ever put on a dashboard or an alert. When we finally counted, it was just under half of every data point our host agents sent.</p><p>I look after monitoring for a large company&#8217;s infrastructure. A few hundred virtual machines each run an OpenTelemetry Collector as the host agent. The agent config lives in a repo, it gets reviewed, and everyone treats that file as the truth about what the fleet is collecting. It wasn&#8217;t.</p><h3>How we noticed</h3><p>Storage was growing faster than the host count. That&#8217;s usually the first sign that something is collecting more than it should, but &#8220;something&#8221; is a wide net. Instead of guessing, we asked the database what it was actually storing. One query, grouping data points by metric name prefix over a week.</p><p>The top line was <code>process.*</code>. Per-process CPU, memory, disk I/O and open handles, for every process on every host, every ten seconds. Just under half of all metric points. Below it, the usual suspects: <code>system.cpu</code>, <code>system.memory</code>, <code>system.network</code>, each a fraction of the size.</p><p>The second number was worse. Over eighty percent of the disk wasn&#8217;t the values at all. It was the attributes: the labels attached to each point, plus the IDs that index them. Per-process metrics are the worst case for this. Every point carries the process name, the PID, the owner, sometimes the full command line. The number is eight bytes. The labels describing it are hundreds.</p><h3>Why it happened</h3><p>The reference config in the repo had the <code>process</code> scraper of the hostmetrics receiver turned off. That&#8217;s the default and it&#8217;s the right default. The config on the hosts had it tur&#173;ned on.</p><p>That divergence must have crept in during an early rollout, on one host image, and then propagated as that image was cloned across the fleet. Nobody noticed, because the agent config is exactly the kind of thing you set once and stop looking at. It works. Metrics flow. No alert fires when you collect too much. The only signal is a storage bill nobody reads line by line, and by the time it&#8217;s big enough to notice, it&#8217;s been wrong for months.</p><h3>What it means</h3><p>Two things, and only one of them is about money.</p><p>The obvious one: we were spending real storage on data with no reader. Turning the scraper back off across the fleet drops metric volume by roughly forty percent. Same infrastructure, same visibility, because nobody was looking at the per-process series anyway.</p><p>The one that stays with me: the repo lied and everyone believed it, for months, with no bad intent anywhere. The config was reviewed. The reference was correct. The gap was between the reference and the machines, and nothing was watching that gap. This is the same failure that sits under every &#8220;the AI gave a confident wrong answer&#8221; story. The map and the territory drift apart quietly, and confidence attaches to the map.</p><h3>What we changed</h3><ul><li><p><strong>Turned the scraper off at the source.</strong> Not a drop filter downstream. If the data has no reader, the cheapest place to stop it is before it leaves the host.</p></li><li><p><strong>Started measuring collected-versus-queried.</strong> The real question isn&#8217;t &#8220;how much are we collecting&#8221;, it&#8217;s &#8220;how much of what we collect does anyone ever look at&#8221;. That ratio is the one worth a dashboard, and it&#8217;s the one nobody builds first.</p></li><li><p><strong>Stopped trusting the config file as evidence.</strong> The agents are the inventory. If you want to know what the fleet collects, ask the fleet, not the repo.</p></li></ul><p>If you run agents at any scale, go run that grouping query against your own telemetry store this week. Group by metric name, sort by count. I&#8217;d bet the top line surprises you, and I&#8217;d bet it&#8217;s something nobody asked for.</p>
